## 1. 功能与优先级（基于当前项目定位）

### 核心功能（High）

- 语音输入与识别（ASR）：将麦克风音频转换为文本，作为用户指令与对话输入。
- 文本到语音（TTS）：将 LLM 回复转换为语音播报，形成完整的语音交互闭环。
- LLM 对话（HTTP/SSE）：通过 Java（Spring AI）承载与模型的聊天/推理，并在前端以 SSE 流式展示结果。
- 桌面端 UI（Electron + Vue3）：会话窗、录音控制、消息展示、状态与错误提示。
- 配置与密钥管理：在后端统一管理与切换模型提供方（Qwen/Gemini），支持本地开发的 CORS/SSE。

### 增强功能（Medium）

- OCR 能力（Python 微服务）：对截图/图片做文字识别，为语音指令与 LLM 工具调用提供信息输入（当前已提供 `backend/golang/files/OCR_api.py`）。
- 基础系统操作桥接（Go）：在不引入第三方 agent 的前提下，按规则映射有限的系统操作（打开应用、读文件等）。
- 会话管理：历史记录、复制/清空、导出（Markdown/JSON）。
- 播放控制：TTS 中断、重播、音量与速率调整。

### 扩展功能（Low）

- 多语言与方言支持（ASR/TTS）：在需要时扩展到多语言识别与播报。
- 离线/弱网模式（可选）：在网络不稳定时提供有限功能（如仅 ASR/TTS）。
- 插件化工具接入：在不使用第三方 agent 的前提下，标准化工具接口（OCR、日历、剪贴板、截图）。

### 本次开发计划（MVP 范围）

- 接入并打通：ASR（SenseVoice 或 FunASR 生态）→ Java LLM（SSE）→ TTS 播放。
- 支持双模型：Qwen3-Max 与 Gemini-2.5-Pro-Thinking 的后端选择与切换（以环境变量/配置驱动）。
- 集成 OCR 微服务：通过 HTTP 调用 `POST /ocr`，在前端展示提取结果并可作为 LLM 的上下文。
- 完成前端基本交互：录音/停止、消息发送、流式渲染、错误与提示。
- 不使用第三方 agent：由 Java 服务进行“有限规则驱动”的工具调用编排，不引入外部代理框架。

## 2. 实现挑战与应对策略

- Windows 音频采集与设备兼容性

  - 挑战：采样率、声卡/驱动差异、麦克风权限与设备切换。
  - 应对：在 Go 层统一采样参数（如 16k/mono）、提供设备列表与默认设备回退；对错误做明确提示与日志记录。
- SSE 流式与 CORS

  - 挑战：开发环境中前端（5173）与 Java 服务（8080）跨域、SSE 长连接稳定性与心跳。
  - 应对：在 Spring Boot 配置全局 CORS；SSE 响应确保 `text/event-stream`、禁用缓存与合适的 keep-alive；前端做断线重连与错误提示。
- 双模型接入差异（Qwen 与 Gemini）

  - 挑战：鉴权、API 形态、消息格式与可选功能差异（如函数调用、流式协议）。
  - 应对：在 Java 服务抽象 `LLMProvider`，分具体实现（QwenProvider、GeminiProvider）；以配置/环境变量切换，统一输出流式与普通回复接口。
- 性能与资源使用

  - 挑战：ASR/TTS 与 LLM 并发调用的 CPU/GPU 占用、内存与启动耗时（尤其 PaddleOCR 首次加载）。
  - 应对：尽可能使用流式；在 Python/OCR 首次启动时明确提示模型下载；对非核心路径使用队列与缓存；在 UI 做加载进度与降级策略。
- 不使用第三方 agent 的编排

  - 挑战：在无代理框架的前提下，工具调用与对话的决策逻辑较简单，易受上下文限制。
  - 应对：采用“规则驱动”的轻量编排：
    - 约定 LLM 的输出中出现标准化的工具触发格式（如 `tool: ocr` 或 JSON 标记），Java 服务检测并调用对应工具，再将结果回填到上下文。
    - 保持工具列表有限与接口稳定（OCR、系统少量动作），避免复杂的自我决策链条。
- 交互与可用性

  - 挑战：语音/文字的双向状态同步、TTS 与 SSE 的时间线一致性、错误处理易于理解。
  - 应对：前端采用统一状态机，明确各阶段（录音中/识别中/生成中/播报中）；对失败场景提供可重试与回退文案。

## 3. LLM 模型采纳与对比

### 采纳方案

- 首选：Qwen3-Max（通义千问）
  - 原因：中文能力强、响应速度与成本较为均衡、在国内网络环境可用性更佳；工具调用/函数生成能力良好。
- 增强：Gemini-2.5-Pro-Thinking（Google）
  - 原因：更强的复杂推理与结构化思考能力，适合需要高可解释度与多步逻辑的任务；作为“高难度问题”fallback。

### 对比维度与结论（简要）

- 语言能力：Qwen 对中文语境与工具调用表达更优；Gemini 在英语/跨领域推理更强。
- 成本与可用性：Qwen 在国内可用性与成本更友好；Gemini 在复杂推理场景的价值更高。
- 接入与生态：二者均可通过 REST/SSE 接入；Java 服务将以提供方适配器方式统一对外接口。

### 具体接入（配置建议）

- Java 服务层提供 `LLM_PROVIDER` 配置：`QWEN` / `GEMINI`。
- Qwen（DashScope 生态）
  - 环境变量：`DASHSCOPE_API_KEY`
  - 兼容模式（OpenAI 风格）或官方 REST，均可通过适配器实现。
- Gemini（Google AI Studio）
  - 环境变量：`GOOGLE_API_KEY`
  - REST/SSE 接入，统一流式输出到前端。

> 本仓库现有 Spring AI 示例配置为 OpenAI 风格（见 README）。在实现适配器时，将提供 Qwen/Gemini 的独立 client 并保持接口统一，不依赖第三方 agent。

## 4. 未来规划功能与价值

- 减少处理等待时间：通过全链路优化降低交互时延（ASR/LLM/TTS）、模型预热与缓存、并发与异步管线、合理分批响应、网络与带宽策略优化。
- 唤醒词与持续监听（可选）：提高免手动的语音交互体验；通过能耗与隐私控制可开关。
- 本地化模型选项（ASR/TTS 轻量版）：弱网场景下保持基本功能可用，增强隐私与成本可控性。
- 上下文记忆与知识库（轻量）：在不引入 agent 的前提下，支持用户本地笔记/文件的检索与上下文补充。
- 插件化工具接口：标准化工具（OCR、Screenshot、Calendar、Clipboard）以 HTTP/IPC 方式接入，简化扩展与维护。
- 跨平台打包（Win/Mac）：提升覆盖面，与 Electron 打包流程打通。
- 安全与隐私：更细粒度的日志与开关，明确数据流向与敏感信息最小化原则。

这些能力能增强产品的可用性（持续语音交互）、可靠性（弱网下仍可用）、扩展性（插件化工具），以及在不同用户场景下的适应性。

## 开发与实现方案（符合约束）

- 架构与通信

  - 前端（`localhost:5173`）→ Java LLM 服务（`localhost:8080`）：`GET /ai/manus/chat?message=...`（SSE）、`POST /ai/chat`（JSON）。
  - 前端/Go → Python OCR（`localhost:5000`）：`POST /ocr`（`multipart/form-data`，字段 `image`）。
  - 前端 → Go：IPC/HTTP（ASR/TTS/系统操作）。
- 语音识别（ASR：SenseVoice/FunASR 生态）

  - 以 Python 微服务或 Go 子进程调用方式实现识别（不引入第三方 agent）。
  - 将识别结果回填到前端并传给 LLM 服务。
- 文本到语音（TTS）

  - 在 Go 层播放合成语音，提供播放状态回调；前端显示进度与控制按钮。
- LLM 调用

  - 在 Java 服务抽象 `LLMProvider`，针对 Qwen/Gemini 实现各自 client；统一输出 SSE/JSON。根据 `LLM_PROVIDER` 配置选择提供方。
- 工具编排（无第三方 agent）

  - 约定有限工具协议：当 LLM 输出包含约定的触发标记（如 `tool: ocr` 或 JSON 格式 `{action:"ocr"}`），Java 服务调用对应工具，并将结果作为上下文继续回复。
  - 工具列表可配置且受限，避免复杂多阶段代理决策。
- 配置与密钥

  - 在 `application.properties` 或环境变量中配置：`LLM_PROVIDER`、`DASHSCOPE_API_KEY`、`GOOGLE_API_KEY`。
  - 开启 CORS，确保前端能在开发环境访问 Java 服务端点；SSE 响应头设置正确。
- 运行步骤（摘录，详见根 README）

  1. 启动 Go 后端：`cd backend/golang && go run .`
  2. 启动 Java 服务：`cd backend/java && mvnw.cmd spring-boot:run`
  3. 启动 OCR 服务：`cd backend/golang/files && python -m venv .venv && .\.venv\Scripts\activate && pip install flask paddleocr && python OCR_api.py`
  4. 启动前端：`cd frontend && pnpm install && pnpm dev`
- 验收标准（MVP）

  - 语音 → 文本：前端录音后，可成功识别并显示文本。
  - 文本 → LLM：将文本发送到 LLM，前端以 SSE 流式展示。
  - LLM → 语音：将回复合成并在桌面播报，可控制停止/重播。
  - OCR：上传图片到 `POST /ocr`，结果在前端展示并可作为上下文输入。
  - 双模型切换：通过配置选择 Qwen 或 Gemini，服务能正确返回结果。
